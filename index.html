01 · 第一章

工具是什么：模型不会伸手，只会点单

第一次看 Agent「打开网页」「生成图片」的人，多半以为模型长了手。真相朴素得多：模型从头到尾只做一件事——读文本、吐文本。所谓工具，是把一份「菜单」塞进上下文，让模型吐出一段格式严格的点单 JSON；真正伸手拿扳手的，是模型之外的运行时代码。

⚓ 1.1一次调用的完整链条

把模型想象成餐厅里只看得见菜单的食客。运行时先把工具清单（名称 + 一句描述 + 参数说明）连同用户问题一起端进上下文；模型读完，吐出点单：{"tool": "generate_image", "arguments": {"prompt": "一只戴工程师帽的柴犬", "count": 2}}——注意它只是文本，模型没有执行任何东西。运行时代码解析这段 JSON，做参数校验，执行真正的函数（发 HTTP、读文件、起任务），把结果序列化成文本回填到对话里，再请模型看一眼结果、继续回答。一个完整的「调用」= 点单 → 端菜 → 回填 → 续答，四步缺一不可。

经典追问：模型真的在「调用」工具吗？不是，而且承认这一点很重要。三个证据：①模型侧的输出永远是纯文本 JSON——没有跳转、没有副作用；②真正执行发生在模型之外的普通代码里，出错、限速、计费都在那层；③模型对执行结果一无所知，直到结果作为新消息回填——所以「回填失败」这种事故模型根本感知不到，只会自顾自地继续编。理解了这一层，后面所有设计（schema、排队、报错）都变得显然：它们全是在给这段「文本协议」补上模型天生没有的东西——约束、耐心和记忆。

⚓ 1.2菜单本身就是工程品

工具清单不是随手一列的注释，它每次对话都常驻上下文。本篇解剖的这台 server 注册了 13 个工具，光工具描述就有约 1600 字——每次对话开始，这些字都先占掉一片窗口（第六章细算这笔账）。描述写得含糊，模型就点错菜：把「生成视频」的活派给「生成图片」，或者自作主张补一个没给的参数。所以工具描述是面向模型的界面文档——写给一个读得极认真、但毫无常识的字面主义者。

02 · 第二章

MCP：一台通用工具台的协议

在 MCP 之前，工具接入是一笔 M×N 的糊涂账：M 个客户端（Claude、Cursor、你自己写的 harness）× N 个工具商（生图、检索、数据库……），每对组合都要手写一份胶水。MCP（Model Context Protocol，2024 年 11 月开源）把这笔账压缩成 M+N：工具商只管实现一次 server，客户端只管实现一次接入，剩下的握手、列清单、调用，全部走同一份协议。

⚓ 2.1协议的地基：JSON-RPC 2.0

MCP 的数据层就是 JSON-RPC 2.0——一种 2009 年定稿的老协议，全部消息只有四种：请求（带 id，要回话）、响应（带同号 id，回答请求）、错误（带同号 id + code/message）、通知（不带 id，说完就走）。id 配对是整台协议的骨架：你发出去的第 3 号请求，回话一定也标着 3 号——并发多条调用也不会串线。本篇 server 的名字在握手报文里就写作 {"name": "ai-image-studio", "version": "0.1.0"}。

经典追问：为什么不用 REST，非要 JSON-RPC？REST 面向资源（GET /images/42），而工具调用面向动作（「执行 inspect_image，参数 mode=position」）——动作没有天然的 URL，硬造资源路由只会产生一堆动词端点。JSON-RPC 把「方法名 + 参数 + id」三件事压进一个信封，单连接双向走，通知类消息（如进度上报）不需要应答也不占 id——工具台这种「一声令下多个动作」的场景，它比 REST 贴身。

⚓ 2.2握手：先对暗号，再点菜

连接建立后，客户端必须先发 initialize：带着自己支持的协议版本号和自身能力清单（我支持工具、我支持采样……）。server 回应它支持的版本与能力，两边就高不就低地锁定一个版本——谈不拢就直接断连，绝无含糊。客户端随后发一条 notifications/initialized 通知表示「暗号对上了」，之后才能 tools/list 拉菜单、tools/call 下单。这条三步握手挡住了两类事故：版本不一致的「鸡同鸭讲」，和客户端一上来就调用工具的「没登记先点菜」。

版本线（官方 spec）关键变化
2024-11-05首版：JSON-RPC 2.0 + initialize 握手 + stdio 传输
2025-03-26引入 Streamable HTTP（替代旧 HTTP+SSE）
2025-11-25生命周期细化，握手与关停行为收紧
2026-07-28核心走向无状态：会话态从协议层剥离，HTTP 部署可水平扩展

传输层只有两种：stdio（server 当子进程拉起，标准输入输出收发——本地工具台的最快路径）和 Streamable HTTP（远程挂个 HTTP 端点）。本篇的画境 server 走 stdio：harness 把它当子进程启动，报文从标准输入进、标准输出回，零端口零鉴权，本机工具台就该这么朴素。

03 · 第三章

schema：菜单即闸门

模型点单不保证老实——它会补你没写的参数、漏掉必填项、把「1 到 4 张」写成 17。schema（JSON Schema）是工具台上唯一的闸门：参数类型、范围、必填、默认值，全在这里声明。闸门越清楚，模型越少越界——它读得极认真，只是没常识。

⚓ 3.1一台真 server 的 schema 长什么样

本篇标本（画境 server）的 generate_image 用 zod 声明，展开后就是一份严格菜单：prompt 必填、1 到 12000 字符；count 整数、1 到 4；waitSeconds 5 到 600；wait 布尔、默认 true。每个字段都挂一句 describe——那是写给模型的说明书（「渠道 ID；不传则自动选第一个启用了生图模型的渠道」）。describe 不是注释，是菜单正文：模型点单时唯一能参考的文本就是它。

标本原样 · generate_image 的菜单（节选）
// zod 声明 → 展开为 JSON Schema，随 tools/list 下发
prompt:        z.string().min(1).max(12000).describe('画面描述（正向提示词）')
providerId:    z.string().optional().describe('渠道 ID；不传则自动选第一个启用了生图模型的渠道')
count:         z.number().int().min(1).max(4).optional().describe('生成张数 1-4，默认 1')
wait:          z.boolean().default(true).describe('是否等待生成完成，默认 true')
waitSeconds:   z.number().int().min(5).max(600).optional().describe('最长等待秒数，默认 240')

经典追问：为什么不信任模型老实传参，非要加闸门？因为模型的输出本质是「续写最像的文本」，不是「执行约束的程序」。没有闸门时三类事故高发：①幻觉参数——给并不存在的字段赋值（静默失效）；②越界值——count 写成 17，下游按 17 张计费；③类型漂移——把数字写成字符串，深夜定时任务里炸给运维看。闸门的另一半价值在报错的方向：校验失败时返回「期望整数、收到字符串、字段名 count」的精确消息，模型下一轮就能自己改——闸门不是不信任，是给模型一条能走回来的路。

范围还有一个隐藏用途：把业务上限写进类型。waitSeconds 的上限 600 不是随手写的——server 端轮询每 2 秒一次、最多等 600 秒（第四章展开），schema 把这条运维事实固化成了类型约束，调用方在点单阶段就知道「等再久也等不过 10 分钟」。

04 · 第四章

长任务：收银台不让你干等

生图 30 到 90 秒、视频几分钟——工具台不能让调用方把消息通道挂死在「干等」上。标本的答案是收银台模式：下单立刻回票（任务 ID + wait=false），票上印着下一步去哪查（hint: 用 get_generation 查询进度）；要等的话也可以等，但最多等 600 秒，超时照样回票让你稍后再查。

⚓ 4.1两种姿势，一条 hint 链

标本把选择权交给参数：wait 默认 true（同步等完），设 false 就是「提交不等待」。但真正的巧思在返回值里的 hint 字段——一条写给模型的路标。同步超时返回 timedOut: true 加一句「仍在生成中，稍后用 get_generation 查询」；异步提交返回 submitted: [id…] 加「用 get_generation 查询进度」。模型读到 hint 就知道下一步该调哪个工具——这比把流程写进系统提示可靠得多：hint 出现在模型最需要它的位置（刚刚收到的结果里），而不是几百轮之前的系统提示里。

标本原样 · 两种返回与真实常量
// wait=false：提交即回票，票上带路标
{ "submitted": ["g_8f3a"], "hint": "用 get_generation 查询进度" }
// wait=true 但超时：如实承认没等到，票照样给
{ "timedOut": true, "hint": "仍在生成中，稍后用 get_generation 查询" }
// 真实常量：POLL_INTERVAL_MS=2000 · DEFAULT_WAIT=240s · MAX_WAIT=600s
// 状态机：queued → running → succeeded / failed（每 2s 轮询一次）

经典追问：为什么不干脆把等待上限拉到 30 分钟，一步到位？三个理由。①通道占用——同步等待期间这条调用往返被挂死，MCP 客户端通常有自身超时（标本所在的 harness 一类默认几十秒），拉满只会换来客户端单方面断连，任务照样死。②体验上的可取消——回票模式里调用方每 2 秒能看一眼进度、能决定放弃；挂死 30 分钟等于把选择权没收。③失败半径——等 30 分钟才报错，浪费的是 30 分钟；等 600 秒承认超时，剩余时间交给票去追。长任务设计的原则就一句：让每一段等待都可观测、可放弃、可续查。

05 · 第五章

错误：把失败说成人话

工具一定会失败：配额用完、上游过载、连接断掉。失败的可怕之处从来不是失败本身，而是失败传回来时是一段没人读得懂的东西。标本在错误上花了三层心思，每一层都有明确职责。

⚓ 5.1错误的三层分类账

层长什么样谁读标本实例
协议层JSON-RPC error：code + message客户端代码没握手就点菜 → 负数错误码断连
工具层isError:true + 文本内容模型配额 429 → 「no available image quota」
业务层hint / 补救建议模型 → 人超时 → 「稍后用 get_generation 查询」

协议层错误说给代码听（数字码好分流重试）；工具层错误说给模型听（isError: true 加一段人话——注意工具失败不是协议错误，调用本身成功送达了，失败的是业务，这样模型才能像读到一份坏结果那样处理它）；业务层 hint 说给下一步听。三层各司其职，谁也不冒充谁。

经典追问：报错为什么要带上「接下来能做什么」？因为收到错误的模型正站在岔路口：它可以放弃、重试、换参数，或者向用户求援——它选哪条路，取决于错误文本里有没有路标。「system cpu overloaded」是事实陈述，模型只能原样转告用户；「上游过载（CPU 99.7%），约 1–5 分钟后可重试，或换 flare 模型」是事实加岔路，模型会自己挑一条走。本篇写作时就撞了一次真的：GIF 渲染上游返回 CPU 过载 503，机器读到的下一句话就是等几分钟或换型号——错误消息直接变成了工作计划。

还有一类更隐蔽的错误：连接死而服务还在。标本的 api() 封装里埋着自愈逻辑——请求抛错时先清掉缓存的 baseUrl、重新发现服务地址，再试一次；第二次仍失败才把「无法连接画境服务（地址）」抛出去。断连重试这类机械动作不该劳烦模型决策，能自愈的先自愈，自愈不了再把现场完整交上去。

06 · 第六章

粒度：一个工具管几件事

工具清单每次对话都常驻上下文——这是设计工具台时最容易被忽略的一笔账。标本的 13 个工具描述合计约 1600 字，意味着每场对话开场先付这笔固定税。于是出现第六章的核心取舍：一件有三种子模式的事，做成一个大工具带 mode 参数，还是三个小工具？

⚓ 6.1两种切法的账本

标本里真有一件这样的三面体：inspect_image——读一张本机图片，模式一 recreate（提取作者原始提示词，复现同款）、模式二 variation（蒸馏成带 {SUBJECT} 占位符的风格模板，换主体批量出图）、模式三 position（反推拍摄机位：高度、俯仰角、焦距、光位、构图关系）。它选择了一个工具 + mode 枚举。账这么算：三合一让菜单少两行、共用同一套「读图」的公共描述；代价是调用方要先理解 mode 这个概念，且三点模式说明挤在同一段描述里。拆成三个工具则相反——每个描述短而聚焦、模型一眼对上意图，代价是菜单变厚、三段公共描述重复出现。

维度一大带 mode拆成三个
菜单开销一段公共描述 + 一行枚举三份描述，公共部分 ×3
模型选对率要先想对 mode 再选工具（两跳）意图直连工具名（一跳）
参数面不同 mode 的专属参数混在一张 schema各自 schema 干净
演进加一种 mode 不动菜单结构加一种 = 菜单多一行

经典追问：工具是不是越多越强？恰恰相反，菜单是负资产也说不定。清单常驻意味着每加一个工具都是每一次对话的固定开销；工具一多，名称相近的工具互相抢意图（search_library 与 random_prompts 之争），模型的选错率反而上升。业界的经验区间在一屏以内——20 个上下；超过就该问一句「这些真都是同一张桌子上该摆的吗」，要么合并（mode 化），要么分层（把冷门工具挪到按需加载的清单）。标本把 13 个工具分成了查询类（list/search/get）、执行类（generate/assemble）、辅助类（polish/random）三组，描述里彼此点名（「生图前用它确认 providerId」），就是给模型画路径。

速查卡：如果只带走十二句

贴在手边的那一页。每句都是前面六章的浓缩，展开版见各章。

① 模型不会伸手，只会点单——调用工具 = 吐一段点单 JSON，执行和回填全是模型之外的运行时的事。
② 没回填模型就失忆——结果必须作为新消息回到对话里，模型才「看见」工具的世界。
③ MCP 把 M×N 份胶水压成 M+N——工具商实现一次 server，客户端实现一次接入，握手列单调用全走同份协议。
④ JSON-RPC 的 id 是骨架——3 号请求回 3 号响应，并发调用不串线；通知不带 id 说完就走。
⑤ 握手三步免事故——initialize 谈版本对能力，谈不拢就断连，没登记先点菜直接被拒。
⑥ describe 是菜单正文不是注释——模型点单唯一能读的说明，含糊一句它就点错一道菜。
⑦ schema 是闸门也是归路——报错带「字段名+期望+实际」三要素，模型下一轮自己就能改单。
⑧ 长任务回票不挂线——wait=false 提交立刻回 ID，票上印着 hint：下一步去哪查。
⑨ 等待要可观测可放弃可续查——同步等有上限（600s），超时如实承认 timedOut 照样递票。
⑩ 错误分三层记账——协议层给代码（错误码）、工具层给模型（isError+人话）、业务层给下一步（hint）。
⑪ 报错带岔路——「过载 1–5 分钟可重试或换型号」是事实加计划，模型会自己挑一条走。
⑫ 菜单常驻上下文，工具不是越多越强——一屏以内是经验线；同一件事多模式，合并还是拆开按选单跳数与菜单账权衡。

收尾：菜单、闸门、票根

工具台设计的全部心思可以压成三件实物：一份菜单（describe + schema，写给一个读得极认真的字面主义者）、一道闸门（校验失败时给出能走回来的路）、一张票根（长任务回票，hint 印在票上）。至于模型——它只负责点单和读信，手长在运行时身上。

这篇的标本是本机一台 653 行的画境 server：13 个工具、zod 菜单、2 秒轮询、600 秒上限、hint 链、断连自愈重试——每一条都对到源码原样。写作当晚它的 GIF 上游真的返回了一次 CPU 过载 503，而那条错误消息自带「等几分钟或换型号」的岔路——第五章的每一个字都是刚发生的事。工具台安好了，剩下的，是把活派给它。
